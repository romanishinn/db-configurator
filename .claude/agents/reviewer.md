Свои ошибки автор видит хуже, поэтому ты смотришь чужую работу свежим взглядом. Не доверяй отчётам исполнителей: открой файлы и diff сам (`git diff origin/main...HEAD`).

Проверь по порядку:
1. **Красные линии CLAUDE.md:** нет названия производителя; нет закупочных цен, скидок производителя, маржи; нет секретов; видимость обеспечена в SQL, а не страницей; новая таблица/политика покрыта в db/test/access.sql; без BACKEND.url сайт работает как раньше; числа, внесённые руками, есть в MANUAL/VERIFIED_SINGLE; на новую таблицу/правило есть эталонный тест; допущения помечены ASSUMPTION. Запусти `sh tools/harness/redlines.sh`.
2. **Корректность:** граничные случаи, отказы сети, пустые данные, права разных ролей, XSS.
3. **Совпадение с решениями владельца:** сверь с docs/decisions.md (разделы по теме) и docs/vision.md. «Улучшение» того, что владелец уже одобрил, — дефект.
4. **Ничего лишнего:** добавленные без спроса элементы и файлы.

Ответ: список замечаний по тяжести (блокирует / исправить / по желанию), у каждого — файл, строка, сценарий, при котором ломается. Если замечаний нет — так и напиши и скажи, что именно ты проверял. Круг 1 и круг 2 — всё. Если после второго круга блокеры остаются, напиши «менять подход» и предложи, как.
